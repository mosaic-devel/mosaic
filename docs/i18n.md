# Internationalization (i18n)

How Mosaic makes its UI translatable. Scaffolding landed in S5; catalogs, the build/install path
and the runtime language switch landed in S54.

## Mechanism: GNU gettext

Mosaic uses **GNU gettext** (PLAN §3.14). The flow is the standard one:

```
  source: _("Open...")          ->  xgettext  ->  po/mosaic.pot  (English template)
                                                      |
                                  translator: fills in -> po/de/mosaic.po ("Öffnen...")
                                                      |
                                   build/install: msgfmt -> <localedir>/de/LC_MESSAGES/mosaic.mo
                                                      |
  runtime: _("Open...") -> gettext() -> "Öffnen..."  (when the locale or $MOSAIC_LANG says de)
```

English needs no catalog: the **msgid is the English text**, so `_()` returns it unchanged when
nothing matches. That is also why a *partial* catalog is a first-class thing rather than a broken
one — an untranslated entry simply shows the English.

## In the code

Include `common/i18n.hpp` and wrap user-facing strings:

- `_("text")` — mark **and** translate at the point of use. This is the common case.
- `N_("text")` — mark for extraction **only** (no translation yet). Use it for strings defined
  far from where they are shown (e.g. a static table); translate later with `_()`.

Both are xgettext's default keywords, so extraction works regardless of how they expand.

`_()` expands to `mosaic::common::i18n::tr()`, which is the single place that calls `gettext()`.
That keeps libintl linked into **only** the `common` module — every other module just includes the
header. `tr()` is null-safe and returns a pointer owned by gettext (stable for the program's
lifetime), so it is safe to hand to FLTK widget labels.

## Directory layout

The invariant in `po/` is: **files are templates, directories are languages.**

```
po/
  mosaic.pot          the English template for the main catalog
  motivate.pot        ... and for the "motivate" satellite domain (po/motivate.md)
  LINGUAS             the shipped language list (generated; see below)
  de/mosaic.po        German main catalog
  pt_BR/mosaic.po     Brazilian Portuguese
  ca@valencia/…       @modifier variants keep the modifier in the directory name
  …
```

This is the KDE/Krita layout, which is what a translator arriving from those projects expects.

## Switching language at runtime

```sh
MOSAIC_LANG=de mosaic              # German UI
MOSAIC_LANG=ja mosaic              # Japanese
MOSAIC_LANG=ca@valencia:ca mosaic  # Valencian, falling back to Catalan
MOSAIC_LANG=en mosaic              # force the untranslated English source strings
```

`$MOSAIC_LANG` exists because the obvious alternative does not actually work: `LANG=ja_JP.UTF-8`
does nothing on a machine that never generated that locale, which would make "try the app in
Japanese" a sysadmin task. A gettext catalog lookup needs no system locale, so an app-specific
variable can always honour the request.

It moves **messages only**. Numbers, dates and collation stay on the system locale, because the
requested locale may well not exist on this machine and a half-applied locale is worse than none.

### The one case it cannot rescue

gettext deliberately ignores the language selection when the message category is `C` — it will not
emit non-ASCII into a locale that cannot represent it. `common/i18n.cpp` works around this by
re-applying `LC_MESSAGES` to a real locale, but if the machine has **no** generated non-C locale at
all (a bare container is the usual case) there is nothing to re-apply and the UI stays English.
Generating any one UTF-8 locale fixes it. Note that `C.UTF-8` does **not** count: glibc excludes it
from the language lookup exactly as it excludes `C`.

### Where catalogs are found

`init()` resolves the catalog directory in this order:

1. the `localeDir` argument, if given;
2. `$MOSAIC_LOCALEDIR` — handy for running straight from the build tree;
3. on macOS, `<bundle>/Contents/Resources/locale`, derived from the executable path so the `.app`
   stays relocatable (the compiled-in path below names a *cross-build* prefix that does not exist
   on the user's Mac);
4. the compiled-in `MOSAIC_LOCALEDIR` (`<prefix>/share/locale`, from `GNUInstallDirs`).

Running uninstalled with no catalogs present leaves everything English, which is correct.

## Building catalogs

`.mo` files are compiled as part of the normal build into `<build>/locale`, a complete locale tree,
so a build-tree binary needs no install step:

```sh
cmake --build build/linux-debug                     # compiles every po/<lang>/*.po
MOSAIC_LOCALEDIR=build/linux-debug/locale MOSAIC_LANG=de ./build/linux-debug/bin/mosaic
```

`msgfmt --check` runs on every catalog, so a format-specifier or header error breaks the build
rather than shipping. The whole thing self-disables when `msgfmt` is absent.

```sh
cmake --build build/linux-debug --target i18n-stats   # coverage per language
cmake --build build/linux-debug --target pot          # regenerate po/mosaic.pot
cmake --build build/linux-debug --target pot-motivate # regenerate po/motivate.pot
```

## Working on a translation

Regenerate the template first if UI strings changed (`--target pot`), then merge it into the
language you are editing and fill in the blanks:

```sh
msgmerge --update po/de/mosaic.po po/mosaic.pot
$EDITOR po/de/mosaic.po        # or Lokalize / Poedit / Weblate
```

Leave an entry you are unsure about as `msgstr ""`. It falls back to English, which is a correct
outcome; a wrong translation has to be *noticed* before it can be fixed.

### Adding a language

1. Add a row to `tools/i18n/languages.py` (English name, endonym, `Plural-Forms`, RTL flag).
2. `tools/i18n/gen_linguas.py` to regenerate `po/LINGUAS`.
3. Create `po/<code>/mosaic.po`, e.g. `msginit -i po/mosaic.pot -l <code> -o po/<code>/mosaic.po`.
4. Re-run CMake (it watches `LINGUAS`) and build.

### The bulk-translation pipeline (`tools/i18n/`)

The S54 catalogs were produced by a fan-out of translators writing plain `id<TAB>translation` TSV,
which `assemble_po.py` then turned into `.po` files. That split exists because hand-written `.po`
syntax is where bulk translation goes wrong — a dropped continuation line or an unescaped quote
corrupts a whole catalog. The tools stay in-tree because the same pipeline is how coverage gets
widened later:

```sh
tools/i18n/core_worklist.py po/mosaic.pot -o /tmp/STRINGS.tsv          # the core subset
tools/i18n/core_worklist.py po/mosaic.pot -o /tmp/STRINGS.tsv --all    # every extracted string
tools/i18n/assemble_po.py po/mosaic.pot --lang de --tsv /tmp/de.tsv --out po/de/mosaic.po
```

⚠ Those numbered work lists are **keyed by position in the template, and are not replayable**.
Adding four strings to one source file shifted 650 of the 1020 positions, so re-running an old
numbered draft against a newer template would silently write 650 wrong translations per language.
The bulk path is for a from-scratch pass only.

**When a few new strings appear** — the normal case after a UI change — use the msgid-keyed path
instead, which cannot drift:

```sh
cmake --build build/linux-debug --target pot                  # 1. re-extract
for d in po/*/; do msgmerge -q --backup=none -U "$d/mosaic.po" po/mosaic.pot; done   # 2. merge
tools/i18n/apply_translations.py po --tsv new.tsv             # 3. fill in the new msgids
```

`new.tsv` is `lang<TAB>english msgid<TAB>translation`. `msgmerge` matches by msgid and leaves
existing work untouched; `apply_translations.py` applies the same safety gate as the bulk path.

`assemble_po.py` is the safety gate. It **rejects** a translation (leaving it empty, so English
shows) when it would break at runtime:

- a printf specifier set that differs from the English — a format/vararg mismatch is a crash;
- a different number of unescaped `/` in an FLTK menu path — that silently reparents menu items;
- an escape sequence `.po` cannot represent.

It also restores the English's leading/trailing spaces, because several msgids are fragments glued
to a value at runtime (`"Version "`, `"by "`) and translators drop the edge space constantly.

## Coverage

S54 translated the **core UI** — 633 of the 1020 extracted strings, i.e. everything except the
Texture Generator dialog and the Settings long-form help, which are the two big specialist string
sets. Those remain `msgstr ""` and show English. Widening coverage is `core_worklist.py --all` plus
another translation pass; nothing in the machinery needs to change.

Across the 74 catalogs (39,883 translated strings in total):

| coverage | languages |
|---|---|
| near-complete (≥600/633) | 57 — af ar be bg bs ca ca@valencia cs da de el eo es et eu fa fi fr gl he hi hr hu id is it ja ka ko lt lv mk mr ms nb ne nl nn pa pl pt pt_BR ro ru sk sl sq sv ta th tr uk uz uz@cyrillic vi zh_CN zh_TW |
| partial (200–599) | 9 — ia cy fy ga kk nds oc ug br |
| high-confidence subset only (<200) | 7 — tg km hne mai wa se xh |
| by design | en_GB (28) — only the strings where British usage genuinely differs |

The partial ones are deliberate. Where a language has no established graphics vocabulary, inventing
one is worse than falling back to English: a wrong term has to be *noticed* before anyone can fix
it, whereas an untranslated string is self-evidently unfinished. Those catalogs also translate
**no** menu paths at all, for the reason in the next section.

These catalogs are **machine-assisted first drafts**. They are a starting point that makes the app
usable in each language, not a finished localisation, and each file says so in its header.
Corrections from native speakers are the expected next step.

## Known limitations

- **Menu paths are single msgids, and translating them is all-or-nothing.** FLTK builds its menu
  tree by splitting each path on `/` and joining siblings by their shared *parent text*. Translate
  `&File/&New...` but leave `&File/&Open...` alone and the menu bar grows **two** File menus, each
  holding half the items — and msgfmt sees nothing wrong, because both entries are individually
  valid. So a catalog must translate every one of the 84 menu paths with a consistent spelling of
  each shared parent, or none of them. `tools/i18n/check_menus.py` verifies exactly this:

  ```sh
  tools/i18n/check_menus.py po --pot po/mosaic.pot
  ```

  `\/` escapes a literal slash inside a label. `assemble_po.py` enforces the segment count;
  per-segment translation would need the menu construction reworked.

  The same rule binds **untranslated** menu items. Dev-only entries must not be added to a
  `_()`-wrapped parent: `menu->add("&Help/Show Canvas FPS", …)` next to `_("&Help/&About Mosaic")`
  forks a second, English "Help" title beside "Hilfe". That is why the debug tools live under their
  own `&Debug` title. And because a localized bar's titles are unpredictable, code must never
  identify a menu by position — `ui/menu_visibility.cpp` names Help, Debug and Edit by the
  callbacks they contain (`tests/test_menu_visibility.cpp`).
- **RTL is text-level only.** FLTK 1.4 links Pango/HarfBuzz/FriBidi, so Arabic, Hebrew, Persian and
  Uyghur *shape and reorder correctly within a label*. Widget **layout** is not mirrored — dialogs
  keep their left-to-right arrangement. Real RTL layout is a separate piece of work.
- **No plurals yet.** There are no `ngettext()` call sites; the UI sidesteps plurals with
  `"%zu layer(s)"`. Catalogs still carry a correct `Plural-Forms` header so the first plural msgid
  does not have to touch 74 files.
- **`tok` (Toki Pona) is not in the set**, though Krita ships it. A 137-word constructed language
  cannot carry "Levels" or "Chromatic Aberration" without coining vocabulary; that is a job for
  someone who actually speaks it.
